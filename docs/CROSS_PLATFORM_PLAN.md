# Markdown Vision for macOS and Linux

## Architecture decision

Keep one copy of the Markdown parser, HTML/CSS, Reader, and Visual/Split editor. Formalize the asynchronous desktop bridge the renderer already uses, and put operating system behavior behind it. Keep the Win32/WebView2 host, NSIS installers, and Windows Explorer preview handler for the first cross-platform release. Windows changes should initially be limited to the bridge and shared renderer.

Use a **Tauri 2 pilot for macOS and Linux**, using WKWebView and WebKitGTK. Tauri supplies window lifecycle, dialogs, IPC, and packaging. Rust and its build tools are developer dependencies. Ship local frontend assets with the application and use the platform webview. Keep frontend packaging independent of host implementation so the same build input feeds Win32 and Tauri. [Tauri architecture](https://v2.tauri.app/concept/architecture/) · [Webview engines](https://v2.tauri.app/reference/webview-versions/)

| Option | Tradeoff | Decision |
| --- | --- | --- |
| Current Windows host + Tauri 2 on macOS/Linux | Keeps the small Windows installer and integrations. Shares host code between the two new platforms and requires maintaining a Windows adapter. | First choice, subject to pilot results. |
| Thin native hosts with C/C++ [webview](https://github.com/webview/webview) or direct platform APIs | Potentially smaller host. Requires more application code for process lifecycle, dialogs, packaging, printing, and local resource handling. | Compare only if the pilot misses a measurable requirement. |
| Tauri on all three platforms | Can unify more host code. Requires proving compatibility with Windows settings, installation, Explorer preview, and performance. | Separate decision after new platforms are stable. |

## Host contract and ownership

- **Shared frontend** owns Markdown parsing and sanitization, editing and undo, search, keyboard command routing, unsaved state, print preparation, and the About UI. Keep the existing `window.desktop` entry points during migration. Document input/output shapes, cancellation and error behavior, adapter readiness, and event subscription. Package a deliberate list of frontend assets so native builds and source checkouts load the same scripts.
- **Desktop adapters** translate commands for open, save, save as, print, fonts, external links, preferences, and optional integration such as updates. Model optional features explicitly. Keep file paths in the host. Work with opaque document IDs, base URLs for allowed images, and defined outcomes such as saved, canceled, conflict, and error. Preserve the Windows result shapes initially and normalize them in one place if needed.
- **Shared Rust service for macOS and Linux** owns open-document identity, read/write semantics, and preferences. Use each OS's native dialogs and configuration directory. Save using a same-directory temporary file, flush it, recheck the original, then use platform-appropriate replacement or no-clobber creation. Define how metadata, symlinks, permission errors, and external changes are handled. Preserve UTF-8 BOM and LF, CRLF, or CR on supported files. Require Save As for mixed line endings or invalid UTF-8, consistent with today's Windows policy. A pre-replace check detects observed conflicts but does not provide locking against an arbitrary concurrent writer; document and test that boundary.
- **Resource boundary** keeps the application UI local. Load document-relative images through a host-owned, read-only resource handler scoped to the current document directory. Canonicalize paths, enforce containment including symlinks, allow only intended image types, and invalidate access when the document changes. Restrict native commands to the app window, block navigation into remote pages, and launch allowed external links in the default browser. Keep filesystem and shell capabilities narrowly scoped. [Tauri capabilities](https://v2.tauri.app/security/capabilities/)
- **Preferences** keep the existing Windows WebView2 profile, origin, and storage keys while Win32 remains the host. Start new installations with versioned, validated preferences in the native per-user config directory and safe font fallbacks. Load asynchronously without overwriting settings changed while the initial load is pending. A future Windows host swap requires a tested, one-time import from the old runtime before the installer replaces it.

## Release gates

1. **Correctness.** New file prompts for a name on first save. Open, Save As, external edits, denied writes, and canceled dialogs preserve user data and dirty state. Exercise Unicode filenames, BOM and line endings, document-relative images after Save As, restart preferences, and native open/close events. Confirm the license link opens in the default browser.
2. **Rendering and editing.** Use `tests/fixtures/Markdown-total-torture-test.md` in Reader, Visual, and both Split layouts. Verify compact and wide tables, narrow panes, long tokens, headings and anchors, direct editing/undo, search, PDF page breaks, repeated table headers, and light/dark preferences. Run actual WKWebView and WebKitGTK checks. Browser-based smoke tests can help with shared logic.
3. **Performance and size.** The acceptable limit is under 10× the comparable baseline for each metric: download size, median cold launch time, and idle memory. For Windows, compare against the current Win32 build on the same machine and architecture. For macOS and Linux, use a thin system webview reference on the same OS and hardware, loading the same assets and doing equivalent startup and initial file-open work. Compare like package formats where possible and report installed app size when formats differ. For each release build, record ten cold launches to first usable window, both empty and with the torture file, and report the median and worst run. Include webview child processes in idle memory. Record runtime versions and separately report Linux runtime dependencies, AppImage size, and universal Mac package size. Report the actual measurements alongside the ratios so substantial differences stay visible even when they pass.
4. **Upgrade and distribution.** Install on clean systems and upgrade an older build on each supported platform. On Windows, test both architectures, a custom install folder, Explorer preview, and retained theme, font, size, line spacing, and page width. Verify macOS Gatekeeper acceptance and Linux dependency installation. Require all selected artifacts before publishing. Keep the existing Windows build path available if a future host replacement fails these gates.
